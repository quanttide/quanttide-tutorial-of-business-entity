# 量潮云简介

## 业务定位

量潮云的目标是成为帮助人类消除人机协作摩擦的第二大脑，核心是减轻认知负担。最终形态是 CoWork/WorkBuddy——用户用自然语言派活，各云作为领域专家被任务调度，系统交付可验收的成果。

平台的方法是找到认知摩擦：从想法到落地之间的摩擦点。产品云回答从产品想法到落地的摩擦，基础设施云回答从基础设施想法到落地的摩擦，各云各回答一个领域内的摩擦。

## 产品形态演化

量潮云从 0.1 演化到 1.0，主线是各云从「互相认识」到「被派活」到「真干活」到「成行家」到「组团队」：

- **门户与协作目录（0.1）**：各云互相认识。协作目录是产品线的中枢，每个云在这里自我介绍：我发布什么、我订阅什么
- **任务工作台（0.2）**：从逛工具转向派活。用户不再记「哪个云干什么」，直接说要什么，系统把任务拆成步骤、标出每步由谁做
- **执行闭环（0.3）**：从给方案转向交付结果。任务派下去，各云真的开始干活，用户从执行者变成验收者——这是 CoWork 模式与聊天工具的本质区别
- **专家生态（0.4）**：每个云沉淀为有方法、有交付物的领域专家，企业把自己的 SOP 和知识库喂给专家
- **项目空间（1.0）**：复杂项目多个专家并行干活，成熟流程沉淀成团队资产，量潮云从工具集合变成真正的数字同事团队

qtcloud Studio 是协作目录的客户端载体。

## 当前现状

协作目录已具备事件目录、契约管理、流程编排三个核心页面，数据暂以本地配置演示。议事云与数据云两个子域已上线，协作目录尚未部署，cloud.quanttide.com 主域空白。

账号与支付子系统正在收尾验收，以招聘政策案例为起点跑通端到端闭环：任务输入、拆解、多模块接力、交付草案、验收。

## 核心困难

量潮云的演化本质是解决三个核心矛盾，而非简单的功能累加：

- **从「工具」到「同事」**：系统第一次接管流程记忆，如果任务拆解不可靠，信任会在第一天崩塌，所以验收机制必须作为一等公民，而不是事后补丁
- **从「设计」到「交付」**：契约从注册表变成运行时验收标准，AI 输出从建议变成交付物，错误成本陡增
- **从「专家」到「系统」**：专家生态的前提是把「会做」变成「能教」，隐式经验显式化是长期的苦功夫

最大的风险是平台建设诱惑：在信任底座和真实业务缺失时先建平台，是最危险的顺序。

## 应对思路：数据驱动的产品研发

量潮云研发的核心方法是数据驱动：用半结构化数据桥接文档与代码。

传统研发中，文档和代码是两条线，靠人来同步——人是最薄弱的环节。量潮云的做法是先把知识中可结构化的部分提炼为 JSON/YAML 契约，各端代码读契约不读 Markdown，形成知识增殖闭环：

档案 → 契约 → 代码 → 新数据 → 档案

每轮循环，档案都变得更精炼，而非传统文档越写越乱。这条链路已在管理后台落地：跨群搜索聊天记录、提取政策、抽取本体、按主题总结，招聘与课堂的政策都从这条链路沉淀。

## 原则

- 从做对的系统到做活的系统
- 云从业务中长出来，先跑通闭环再横向复制，不被平台建设诱惑
- 0.1 的最小可用比想象中小
- 系统首先让产研团队内部用起来，最大程度验证系统是否有效
- 「资本家系统」是设计启发：让老板和员工都干得更舒服，避免陷入零和博弈

## 未来方向

- 账号与支付：身份认证基于零信任假设，先做角色权限（RBAC），复杂后再升级策略控制；用代金券机制加快支付验证
- 客服云：储电站模式、内外一体的工单系统，让系统在无人值守时正常运转
- 项目空间：多 Agent 并行，成熟流程沉淀复用，个人效率跃迁为组织能力
